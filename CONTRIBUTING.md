# Contributing to fresta

Спасибо за интерес к проекту. Ниже — короткий гайд по тому, как внести вклад
эффективно и не сломать архитектуру.

## Главное

- **Проект — не «новый протокол» и не «новое крипто».** Это **recon (поиск щели)
  + оркестрация + чистая сборка уже известных рабочих методов**. См.
  `docs/knowledge.md` §0 (TL;DR).
- **Не вводите внешние зависимости** в рантайм-код без обсуждения. Всё собрано
  на stdlib (`urllib`, `ssl`, `subprocess`, `argparse` — и больше ничего).
  Зависимости допустимы только в `pyproject.toml [project.optional-dependencies]`
  для dev-инструментов (ruff, mypy, pytest).
- **Терминология.** В `docs/knowledge.md` §5 и `docs/ROADMAP.md` сохранена
  устоявшаяся «Метод N / Фаза N» нумерация. В `docs/manuals/` используются
  **самодокументирующиеся имена** (`vless-vps` / `ycloud-function` / `recon`).
  Обе системы — синонимы, не путаница.

## Workflow

1. **Issue сначала.** Перед PR откройте issue (багрепорт или фичереквест) —
   обсудим подход. Это экономит время и для вас, и для нас.
2. **Форк → ветка → PR.** Сделайте форк, ветка от `main` с говорящим именем
   (`fix/recon-typo`, `feat/bench-script`, …).
3. **Прогоните тесты локально:**
   ```bash
   bash scripts/tests/run_tests.sh        # Linux/macOS/WSL/Git Bash
   powershell scripts/tests/run_tests.ps1 # Windows
   ```
   На Linux/macOS/WSL дополнительно:
   ```bash
   make lint      # ruff + проверка стиля
   make test      # то же, что run_tests.sh
   ```
4. **CI должен быть зелёным.** GitHub Actions прогоняет те же smoke-тесты на
   каждом push. PR не мерджится, пока CI не зелёный.
5. **Правьте доки.** Любое изменение API скрипта → обновите:
   - `docs/knowledge.md` §6 (что построено) и/или §9 (структура репо)
   - `docs/ROADMAP.md` (статус чек-боксов)
   - `CHANGELOG.md` (секция Unreleased)
   - `docs/manuals/<метод>/...` (если меняется пользовательский сценарий)

## Структура PR

Заголовок — `<type>(scope): <description>`, типы:
- `feat` — новая функциональность (скрипт, фича, гайд).
- `fix` — баг-фикс.
- `refactor` — без изменения поведения (только структура/чистка).
- `docs` — только документация.
- `test` — тесты.
- `chore` — обвязка (CI, линтеры, .gitignore).

В описании:
- **что** изменилось (1–3 строки);
- **зачем** (какую проблему решает);
- **как проверить** (шаги воспроизведения / команды);
- **скриншоты / логи** — для всего, что трогает сетевое поведение;
- ссылка на issue (`Closes #N`).

## Что НЕ принимаем

- Новые криптопротоколы / собственные схемы обфускации (не наш профиль —
  есть Reality/XTLS).
- Внешние зависимости в рантайм-коде (см. «Главное»).
- PR без issue (исключение — опечатки в доках).
- Удаление/замена/ослабление SSRF-блока в `yc_function/handler.py`.
- Слабые/предсказуемые секреты в `gen-keys.sh`-эквивалентах.

## Юридическая рамка

Проект — инструмент. Не поддерживает обход санкций, спам, сканирование чужих
серверов, любые формы причинения вреда. Участие в проекте = согласие с
`docs/specification.md` §11 и `LICENSE`.

## Лицензия

Внося изменения, вы соглашаетесь на их распространение под лицензией MIT
(см. `LICENSE`).
