# Project «Щель» — обход IP-белых списков через дружественный CDN

> Рабочее название, переименуй. Идея — найти и переиспользовать «щель» в белом списке: IP, который оператор обязан пропускать, но через который можно гнать произвольный трафик.

---

## 1. Проблема

Мобильный оператор в городе применяет **белый список IP**: пропускаются только пакеты к разрешённым адресам/подсетям (Госуслуги, банки, маркетплейсы), всё остальное дропается. Блокировка происходит **по адресу назначения, до анализа содержимого**. Поэтому маскировка протокола (Reality, обфускация, VLESS) здесь бесполезна — она помогает против DPI, который смотрит *что* за трафик, а белый список смотрит *куда* идёт пакет.

Вывод: любой туннель к неразрешённому IP мёртв на старте. Единственная лазейка — отправлять трафик **на IP, который уже в списке**, но так, чтобы он шёл дальше, куда нам надо.

## 2. Threat model

- **Основное**: IP-whitelist на уровне оператора/ТСПУ. Allow только список IP/CIDR.
- **Вероятно поверх**: SNI-инспекция и/или DPI на разрешённых направлениях (на случай, если кто-то фронтит). Может появиться позже как реакция.
- **Возможно**: активный пробинг наших endpoint'ов, попытка отличить наш трафик от легитимного к тому же CDN.
- **Чего НЕ предполагаем**: расшифровку TLS (MITM с подменой сертификата) — это другой уровень угрозы, при нём вся затея отдельно пересматривается.

## 3. Ключевая идея

Если разрешённый сервис хостится за крупным CDN (Cloudflare, Fastly, CloudFront), то **anycast-IP этого CDN попадают в белый список целиком** — оператор не может вырезать отдельный сайт за CDN, не задев тысячи других. Мы разворачиваем **свой код на том же CDN** и используем его IP как вход:

1. Клиент открывает TLS на edge-IP CDN (он в списке → проходит).
2. Внешний SNI — легитимный домен этого CDN. Снаружи выглядит как обычный визит на разрешённый сайт.
3. Внутри (Host-заголовок / Worker-route / путь) трафик маршрутизируется на **наш** relay на том же CDN.
4. Relay форвардит на наш VPS-exit → открытый интернет.

Это «захват разрешённого сервиса как транспорт» в чистом виде. Классический домен-фронтинг крупные облака прикрыли (AWS/Google), но: (а) Cloudflare Workers по-прежнему позволяют маршрутизировать по hostname, (б) на AWS Lambda фронтинг местами жив, (в) даже без классического фронтинга достаточно, чтобы edge-IP CDN были в списке и мы могли крутить на нём Worker.

## 4. Архитектура

| Узел | Где крутится | Чьё | Роль |
|------|-------------|-----|------|
| Клиент (sing-box / xray) | устройство или роутер | твоё | заворачивает трафик в туннель, ставит нужный SNI |
| CDN edge | anycast CDN | чужое (в списке) | точка входа, IP проходит белый список |
| Worker / relay | serverless на том же CDN | твоё (деплой) | принимает туннель, форвардит дальше |
| Exit | VPS | твоё | выпускает трафик в открытую сеть |
| Оркестратор | VPS / serverless | твоё | раздаёт конфиги, ротирует фронты, мониторит живость |

**Минимальная конфигурация**: клиент + Worker (Worker сам `fetch`-ит цель, без VPS). Подходит для текста/API, упирается в лимиты Worker по CPU-времени и трафику.

**Полная конфигурация**: клиент → Worker (только relay) → VPS-exit (Xray/sing-box inbound). VPS даёт стабильный выход, полноценный UDP/TCP, отсутствие лимитов Worker.

## 5. Tech stack (не изобретаем велосипед)

Транспорт «VLESS/Trojan + WebSocket + TLS через CDN» — **решённая задача** (Xray-over-CDN, гайдов масса). Наш велосипед — не крипто и не протокол, а **recon-движок и оркестрация под whitelist**. Берём готовое:

- **Edge (приоритет)**: Cloudflare Workers — огромный anycast-диапазон (макс. шанс, что разрешённый сервис именно там), бесплатный тариф, маршрутизация по hostname, `fetch` наружу.
- **Edge (резерв)**: AWS Lambda Function URLs / CloudFront — подход из работы CensorLess (распределение по регионам, дороже блокировать).
- **Транспорт**: VLESS+WS+TLS либо Trojan-WS. Реализация — Xray-core или sing-box (оба умеют v2ray-transport через CDN).
- **Клиент**: sing-box (есть Android/iOS/OpenWrt). На роутере — лучший вариант: настроил раз, вся сеть за ним.
- **Оркестратор**: твой стек (FastAPI или Laravel) — выдаёт конфиги, ведёт список живых фронтов, ротирует, шлёт health-check'и.

## 6. Фаза 0 — разведка (GO / NO-GO) ⚠️

**Это решает, имеет ли проект смысл. Делать первым, до любого кода туннеля.**

Скрипт-ресёрчер:
1. Собрать список разрешённых доменов/IP (из того, что реально открывается на мобильном; плюс при возможности — выгрузка whitelist оператора).
2. Резолвить домены → IP → определить ASN/CDN (whois, ipinfo, Team Cymru).
3. Проверить, есть ли среди них Cloudflare / Fastly / CloudFront / другой CDN, где **мы можем развернуть код**.
4. **PoC-проверка лазейки** прямо с ограниченного мобильного:
   - TCP-connect к edge-IP CDN из белого списка — проходит?
   - TLS-handshake с легитимным SNI — проходит?
   - WebSocket-апгрейд к нашему тестовому Worker через этот edge — доходит?

**Если да** → щель есть, идём в Фазу 1.
**Если нет** (whitelist — голые IP без CDN) → честно: подход неприменим, нужен другой вектор (или задача нерешаема этим способом). Лучше узнать за 1–2 дня, чем за месяц.

## 7. MVP (Фаза 1)

Минимум, доказывающий сквозной проход:
- Один Worker на Cloudflare как relay.
- Один разрешённый CF-домен как фронт (SNI).
- sing-box на телефоне с ручным конфигом.
- Без авторотации, без VPS — Worker сам `fetch`-ит тестовую цель.
- Критерий успеха: с мобильного под whitelist открывается заведомо заблокированный ресурс.

## 9. Риски и честные ограничения

- **NO-GO на Фазе 0**: если в whitelist нет CDN — проект мёртв сразу. Это не провал, это экономия времени.
- **ToS CDN**: фронтинг/проксирование нарушает условия Cloudflare/AWS. Worker могут забанить → нужны запасные аккаунты/проекты, и ротация по Фазе 3 частично это закрывает.
- **Арм-рейс**: оператор может добавить SNI-инспекцию или DPI поверх whitelist и начать резать по SNI-mismatch или паттернам WebSocket. Тогда нужен ESNI/ECH, fragment, более аккуратная маскировка.
- **Пропускная способность**: free-tier Worker ограничен по CPU-времени и числу запросов. Текст/мессенджеры — ок, видео — тяжело. VPS-exit снимает часть, но Worker остаётся узким горлом на входе.
- **Один статичный exit-IP VPS** — отдельная точка отказа на выходе (но он не виден оператору, виден только CDN'у).

## 10. Что НЕ строить

- Не изобретать протокол и не писать своё шифрование. VLESS/Trojan + WS через CDN уже есть.
- Не пытаться «победить» whitelist более хитрым крипто — он крипто не смотрит.
- Вся ценность — в **recon-движке** (поиск щели) и **оркестрации фронтов** (ротация, мониторинг). Это и есть то, чего нет в готовом Xray.

## 11. Юридическая и этическая рамка

Обход операторских ограничений — серая зона, регулирование зависит от юрисдикции, и нарушение ToS CDN — отдельный риск (бан аккаунта как минимум). Это инструмент доступа к открытому интернету; оценку рисков и решение о реализации принимаешь сам. Документ описывает техническую картину как она есть в открытых исследованиях (домен-фронтинг, CensorLess, meek/Psiphon/Lantern).
